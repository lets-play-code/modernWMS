# ModernWMS 拣货功能增强练习说明（学员版）

> 本文档面向学员，重点说明业务背景、功能目标、关键概念、业务场景与练习数据准备方式。

---

## 1. 这次练习要解决什么问题

ModernWMS 当前已经具备基本的出库主流程，但在“仓内现场执行拣货”这一段，仍缺少更贴近实际业务的能力。

这次练习要补齐的不是一个全新的业务模块，而是对现有发货流程中的“拣货”环节做增强，让系统能够更好地支持：

- 从待拣货任务中组织现场工作
- 给拣货员提供更适合执行的拣货清单
- 记录谁完成了拣货、谁完成了复核
- 在不破坏现有后续流程的前提下，把出库流程继续推进到打包、称重、出库、签收

换句话说，这次练习关注的是：

> **如何让系统从“能推进状态”，提升为“能支持现场拣货执行与复核”。**

---

## 2. 业务背景：拣货发生在什么时间

在仓库管理系统里，拣货通常发生在**出库执行阶段**。

你可以先用下面这条主线理解它在整体流程中的位置：

**入库 / 上架 → 库存存放 → 创建发货单 → 确认出库 → 待拣货 → 拣货 → 拣货复核 → 打包 → 称重 → 出库 → 签收**

本次拣货增强练习的核心观察点仍然落在：

- 发货单已经进入待拣货阶段
- 系统已经知道这些货需要从仓内哪些位置取出
- 仓库现场接下来要真正去拿货、核对、放行

因此，学员首先需要建立一个正确前提：

> **这里的拣货，是出库前的仓内取货动作。**

---

## 3. 功能属于哪个模块，与哪些功能有关

这次增强功能属于 **发货管理** 模块，主要落点在：

- **待拣货**：现场开始执行前的工作列表
- **已拣货**：完成拣货复核后的状态
- **后续环节**：打包、称重、出库、签收

它与现有功能的关系可以这样理解：

### 3.1 上游关系

在进入待拣货之前，系统已经完成了出库确认，发货任务已经成立。

也就是说，拣货不是凭空开始的，而是承接前面的发货业务。

### 3.2 同层关系

系统里已经有“查看商品明细”之类的能力，用来查看某一张发货单对应的底层执行信息。

这次新增的“拣货单”不是为了替代这些能力，而是补充一个更适合现场执行的视角。

### 3.3 下游关系

拣货完成后，发货流程还要继续走到：

- 打包
- 称重
- 出库
- 签收

所以这次增强必须和现有主流程兼容，不能因为拣货功能增强而把后续流程卡住。

## 4. 先建立几个关键业务概念

如果你之前没有接触过 WMS，这一部分很重要。

### 4.1 发货单

发货单表示这次要把什么货发给哪个客户，是出库业务的核心业务单据。

### 4.2 待拣货

待拣货表示这张发货单已经进入仓内执行阶段，但货还没有被实际拣出。

### 4.3 拣货明细

拣货明细可以理解为“系统分配给仓内执行的底层取货任务”。

它更贴近系统执行层，通常会细到商品、库位、数量等维度。

### 4.4 拣货单

本次练习里的“拣货单”，更接近一张**给现场人员看的执行清单**。

它的重点不是表达客户订单本身，而是回答现场问题：

- 去哪个仓库 / 库位拿货
- 拿什么商品
- 拿多少
- 这些货分别对应哪些发货任务

因此你需要特别区分：

> **发货单是业务单据，拣货单是执行清单。**

### 4.5 相关发货单

当多张发货单都需要同一种商品时，现场人员可以一起拣，但业务上仍然要知道这些货最终分别属于哪些发货单。

这就是“相关发货单”的意义。

### 4.6 拣货员与复核员

这两个角色不是一回事：

- **拣货员**：实际去库位拿货的人
- **复核员**：确认这张发货任务已经拣完、可以进入下一步的人

系统需要能区分这两层责任。

## 5. 本次需要补齐的业务能力

### 5.1 从待拣货列表生成拣货单

仓库现场往往不会一张发货单一张发货单地零散处理，而是会把一批待拣任务整理成更便于执行的拣货清单。

因此，学员需要补齐这样的业务能力：

- 在待拣货列表里选择多条待处理任务
- 生成一张可供现场执行的拣货单
- 让用户能查看并打印这张拣货单

### 5.2 拣货单要服务“现场执行”而不是“纯系统展示”

一张有价值的拣货单，应该能帮助现场更高效地完成工作。

所以它至少需要做到：

- 能把适合一起拣的任务组织在一起
- 不会把不同库位的任务错误混成一条
- 让使用者知道每一条拣货项背后对应哪些发货任务

### 5.3 支持拣货员逐步确认执行结果

现场拣货不是只看清单，还需要把执行结果记录回系统。

因此，系统应支持拣货员对已完成的拣货任务进行确认，并留下操作人信息。

### 5.4 支持在复核前纠正错误

现场操作存在拣错、误确认、需要回退重做的情况。

因此，在整单复核前，应允许对已经确认的明细进行撤销或纠正。

### 5.5 支持整单复核并进入下一步

当一张发货任务确认已经拣完后，需要有人从业务上做最终确认，使其可以进入后续打包、称重、出库流程。

这一步在业务语义上更接近“拣货复核”，而不是单纯的“状态推进”。

### 5.6 全流程留痕

系统增强后，使用者应能在合适的位置看出：

- 谁拣了货
- 谁做了复核

这样后续查询、追责和教学演示才有依据。

## 6. 典型业务场景

### 场景一：多张发货单共享同一种商品

仓内同时有多张发货单都需要同一个商品，而且这个商品刚好都从同一个库位取货。

对现场来说，这些任务可以合并考虑，减少重复行走和重复查看。

但合并后，系统仍然需要保留这些货分别属于哪几张发货单。

### 场景二：同一种商品分布在多个库位

仓库里同一种商品不一定只放在一个位置。

如果需要分别从两个库位取货，那么现场执行时就必须拆成两条任务，因为它们对应的是两次不同的到位取货动作。

所以：

> **同商品可以聚合，但不能跨库位错误合并。**

### 场景三：先做明细确认，再做整单复核

较细致的执行方式是：

1. 拣货员逐条完成拣货
2. 系统记录每条任务的执行人
3. 复核员再对整张发货任务做最终确认

这更符合“先执行、后复核”的现场逻辑。

### 场景四：发现错误，需要在复核前撤回

如果某条拣货任务已经被确认，但现场发现拿错货、数量有误或需要重新处理，那么在整单复核前应允许撤回。

这体现的是业务纠错能力，而不是技术细节。

### 场景五：兼容现有主流程

即使现场没有逐条完成所有明细确认，整单流程仍然不能被完全堵死。

系统应在增强后继续支持原有的主流程推进方式，保证后面的打包、称重、出库仍然能正常进行。

## 7. 本次练习的范围边界

本练习聚焦于“出库前的拣货增强”，不要求你重做整个仓储系统。

以下内容不属于本次重点：

- 重建完整入库链路
- 设计独立的 PDA / 手持终端方案
- 引入波次算法、路径优化算法
- 重做整套权限模型
- 把拣货设计成一个全新的独立业务系统

请尽量把分析范围控制在：

> **发货管理中的待拣货、拣货执行、拣货复核，以及它与后续流程的衔接。**
